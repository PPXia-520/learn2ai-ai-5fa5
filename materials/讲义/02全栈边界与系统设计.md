# 讲义二：把需求组织成一个全栈系统

## 学习目标

能够解释一次请求经过哪些模块，每条规则由哪里执行，以及如何用文件保持 AI 的工作方向。

## 一次报名的请求路径

浏览器展示活动和用户信息，发送请求；服务端解析并校验请求，执行报名规则；数据库保存已确认的事实；服务端把结果返回页面。测试从这个外部行为出发检查系统。

需要区分三件事：界面显示的状态、接口返回的结果、持久化记录的事实。页面上的剩余名额可能已经过时，因此最终确认需要依据服务端执行结果。按钮禁用能减少误操作，但用户仍可能重新打开页面或直接发送请求。

## 先明确不能被破坏的规则

所谓关键规则，是系统在所有受支持操作后必须保持的事实。例如“不超过限额”和“同一身份最多一条有效记录”。先用自然语言写清楚，再决定它对应哪些输入、接口与数据约束。

稳定身份与展示信息可能不同。请使用活动字段资料解释二者，而不是依据字段名猜测。一个字段显示在页面上，并不意味着它适合判断唯一性。

## 模块职责

| 部分 | 需要回答的问题 |
| --- | --- |
| 页面 | 展示哪些数据？用户怎样知道正在请求、成功、重复、已满或请求失败？ |
| 接口 | 接受什么输入？拒绝哪些输入？怎样表达不同结果？ |
| 数据存储 | 保存什么事实？哪些约束可由数据库保障？如何跨重启保留？ |
| 验证 | 如何准备初始状态、发送真实请求、检查实际记录并重现结果？ |

模块划分应减少歧义，而不只是列出文件夹。比如“接口检查身份，数据库约束保存时的唯一性，测试覆盖直接请求”，比“采用前后端分离架构”更能说明责任。

## 接口契约与失败路径

为每个接口写明路径、输入、成功结果和失败结果。报名接口需要区分新增成功、已报名、已满、非法输入和技术故障。具体 HTTP 状态码可以讨论，但业务含义必须稳定，页面和测试使用同一契约。

设计时也要回答：读取状态失败怎么办，提交时网络中断怎么办，数据库暂时无法写入怎么办。技术故障不能被解释为“报名已满”，客户端也不能在没有确认时显示成功。

## 数据与取舍

一个本地原型可以用一张活动表和一张报名表表达活动容量及报名记录。你也可以提出更简单的方案，但要解释固定配置与数据库事实怎样保持一致。

不要为单活动作业建立账号中心和复杂微服务。也不要因为范围小就把已确认记录只存入浏览器或内存。方案复杂度应服务于需求，性能或安全保证只能在已实现、已验证的范围内说明。

## 把设计变成 AI 可持续读取的约定

系统设计至少保存：范围与来源、关键规则、请求路径、模块职责、接口契约、数据约束、测试映射、未解决问题。

每完成一个模块，让 AI 重新读取设计并指出对应要求；发现变更时先解释，再由你决定更新设计。这样，后续代码生成可以遵循明确约定，教师也能检查“设计”和“实现”是否一致。

## 课堂练习

1. 用五句话描述一次报名从点击到持久化的过程。
2. 指出仅在页面检查重复会遗漏什么路径。
3. 把需求依据表中的每条关键结论标到模块和测试。
4. 为技术故障与名额已满分别设计可理解的响应。

进入实现前，你应能解释这些决定。图形架构图可以辅助说明，清楚的文字和接口表同样有效。
