# 报名接口测试场景与预期

当前作业：校园开放日报名系统（`50b7cb48-b39b-4da1-aeef-3eb35f66bb51`）  
编写日期：2026-10-21  
执行脚本：`tests/verify_required_scenarios.py`

## 测试原则

- 每次启动服务都使用独立的临时 SQLite 数据库，不读取 `data/registrations.db`，也不依赖已经运行的 8000 端口服务。
- 报名请求通过真实 HTTP 发送，不使用 mock 接口，不直接调用业务函数代替请求。
- 最终判断以 SQLite 实际记录为准；响应只作为请求结果的证据之一。
- 并发场景使用多个线程同时发起请求；每次 99+20 场景都使用新的数据库。
- 文档先列出预期；实际结果写入 `verification/required-scenarios-results.json`，不把预期改写成结果。

## S1：两个不同 student_id 使用同一姓名

| 项目 | 内容 |
| --- | --- |
| 初始状态 | 空数据库 |
| 请求 1 | `POST /api/registrations`，`student_id=S-SAME-NAME-1`，`name=同名同学` |
| 请求 2 | `POST /api/registrations`，`student_id=S-SAME-NAME-2`，`name=同名同学` |
| 预期响应 | 两次都返回 HTTP 201，结果均为 `registered`；剩余名额依次为 99、98 |
| 预期数据库 | 共 2 条记录；两个 `student_id` 都存在且不同；两条记录的 `name` 都是“同名同学” |
| 说明 | 姓名不是唯一标识，同名不能触发查重 |

## S2：同一 student_id 改名后再次报名

| 项目 | 内容 |
| --- | --- |
| 初始状态 | 空数据库 |
| 请求 1 | `POST /api/registrations`，`student_id=S-RENAME`，`name=原名同学` |
| 请求 2 | 同一 `student_id`，`name=改名同学` |
| 预期响应 | 请求 1 返回 HTTP 201 `registered`；请求 2 返回 HTTP 409 `already_registered`；请求 2 返回的原姓名为“原名同学” |
| 预期数据库 | 只有 1 条 `S-RENAME` 记录；`name` 仍为“原名同学”；`created_at` 与首次报名时相同；总记录数为 1 |
| 说明 | 再次报名不新增记录，也不覆盖首次保存的展示姓名 |

## S3：空白身份

| 项目 | 内容 |
| --- | --- |
| 初始状态 | 空数据库 |
| 请求 | 依次提交 `student_id` 为 `""`、`"   "`、`"\t"`、`"\n"`、`" S1"`、`"S1 "` 的报名，姓名均为“空白测试” |
| 预期响应 | 每个请求都返回 HTTP 400，结果均为 `invalid_student_id` |
| 预期数据库 | 记录数仍为 0；剩余名额仍为 100 |
| 说明 | 空字符串、纯空白和首尾空白都在进入写入事务前被拒绝；不替平台 trim 身份 |

## S4：已有 99 人时 20 个新学生同时抢最后一个名额（连跑 5 次）

| 项目 | 内容 |
| --- | --- |
| 初始状态 | 每一轮都使用新的空数据库，先用真实 HTTP 顺序写入 99 名不同学生，数据库记录数为 99 |
| 并发请求 | 20 个不同的新 `student_id`，使用 20 个线程在同一个起点同时发 `POST /api/registrations` |
| 每轮预期响应 | 恰好 1 个 HTTP 201 `registered`；其余 19 个都是 HTTP 409 `full`；不应出现 `busy` 或 `storage_error` |
| 每轮预期数据库 | 总记录数恰好 100；只存在 1 个本轮新身份的成功记录；没有第 101 条记录；成功记录的姓名正确 |
| 重复次数 | 连续执行 5 轮，每轮都重新建立 99 条记录并重新并发；5 轮全部满足上述预期才算通过 |
| 说明 | 这是对“查重、查名额、写入在一个 `BEGIN IMMEDIATE` 事务中”的容量边界验证，不用预先算好的结果代替请求 |

## S5：服务重启后读取

| 项目 | 内容 |
| --- | --- |
| 初始状态 | 新建隔离数据库，启动服务 |
| 写入 | 通过真实 HTTP 报名 `S-RESTART`，姓名“重启前姓名” |
| 重启 | 停止服务进程，用同一个数据库路径重新启动服务 |
| 预期响应 | 重启后 `GET /api/registrations/S-RESTART` 返回 HTTP 200，`registered=true`，姓名仍为“重启前姓名”，剩余名额为 99 |
| 预期数据库 | 重启前后总记录数都为 1；记录内容和 `created_at` 不变 |
| 说明 | 读取的是持久化数据库，不是进程内缓存 |

## 执行命令

在成果目录运行：

```powershell
python tests\verify_required_scenarios.py
```

脚本会在结果文件 `verification/required-scenarios-results.json` 中记录每个场景的预期、实际响应摘要、数据库检查和通过/失败状态。任何一项不符合预期，脚本以非零状态退出。
