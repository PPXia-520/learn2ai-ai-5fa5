# 校园开放日报名系统需求说明

校园开放日有一场限额 100 人的活动，需要一个可以运行的报名系统。学生在 AI 协作中完成本地课程原型，解释自己的设计，并验证关键业务规则。

## 活动规则

- 活动名称为校园开放日 AI 实践工作坊。
- 名额上限为 100 人。
- 同一活动中，同一学生只能保留一条有效报名记录。
- 报名成功后显示明确确认，剩余名额显示与服务端数据一致。
- 名额已满或重复报名时，系统给出可理解的结果。
- 页面区分等待、成功、业务拒绝与技术故障；没有服务端确认不能显示报名成功。
- 重启服务后，已经确认的报名记录仍然存在。

## 需要先检索确认的信息

从活动资料索引进入原始资料，核查本届如何识别同一学生、报名需要哪些字段，以及往届表单哪些内容不再适用。先提交需求依据表，写明来源、版本、适用范围、选择理由和准备验证的方法，再进入系统设计与编码。

继续检索所选数据库的官方文档，核查唯一性、身份缺失和并发写入相关语义。技术检索笔记要说明结论如何用于本项目。

## 原型范围

交付一个本地可运行的报名页面、报名接口、持久化存储和验证脚本。使用虚构学生标识和独立测试数据，不接入真实学校账户、支付和公网部署。

虚构学生标识由课程测试环境提供，用于验证同一标识的唯一报名规则。本原型不声称完成真实身份认证，也不能阻止用户伪造多个身份；学生需要在成果中说明这个范围。

## 验收条件

| 场景 | 必须保持的结果 |
| --- | --- |
| 首次正常报名 | 增加一条有效记录，并返回可理解的确认 |
| 两个不同学生使用相同姓名 | 两人均可正常报名，姓名不作为去重依据 |
| 已报名学生改变显示姓名再次请求 | 不新增报名，姓名变化不产生新身份 |
| 学生身份字段缺失、null、空字符串或纯空白 | 拒绝请求，不写入记录、不占用名额 |
| 学生身份不是字符串 | 拒绝请求，不写入记录、不占用名额 |
| 同一学生并发提交 20 次 | 最终仅增加一条记录，不重复占用名额 |
| 已有 99 人，20 名新学生并发请求 | 仅新增一人，总数为 100 |
| 已有 100 人，新学生直接请求接口 | 不新增记录，明确说明名额已满 |
| 重启服务后读取 | 已确认的记录与人数不丢失 |

验证应通过真实接口请求，并核对持久化记录。每个场景使用独立或重置后的测试数据，记录请求、响应和最终状态。仅检查页面按钮、观察一次正常报名或模拟成功返回值，不能覆盖以上条件。

## 学生需要解释的选择

1. 所选技术依据哪些当前资料，为什么适合这个课程原型。
2. 本届身份和收集字段依据什么，如何处理与往届资料的差异。
3. 检索结论如何进入页面、接口、数据与测试的职责设计。
4. 同一学生一次和总数不超限这两条规则，如何在重复及并发请求时成立。
5. 验证实际覆盖了什么，哪些结论仍不能保证。
