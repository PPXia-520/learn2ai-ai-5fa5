# 校园开放日报名系统

## 一、任务说明

校园开放日 AI 实践工作坊需要一个本地可运行的报名系统。你要把活动资料中的业务要求转化为页面、接口、持久化数据和可验证的行为，并说明自己如何判断、设计、借助 AI 和核对结果。

允许使用 AI 学习概念、检索资料、比较方案、编写代码、生成测试和解释输出。允许 AI 编写全部或部分代码。代码由谁编写不作为评分依据。

你仍需对以下内容负责：

- 哪些资料适用于本届活动；
- 哪些要求必须进入系统；
- 关键规则在哪里执行；
- 测试是否实际运行；
- 结论能够支持到什么范围。

## 二、项目范围

交付本地课程原型，至少包含：

- 一个可以操作报名流程的页面；
- 接收报名请求的服务端接口；
- 重启后仍能读取数据的持久化存储；
- 使用虚构学生数据运行的验证方式；
- 启动、停止、访问和数据隔离说明。

参考技术组合为 Python、FastAPI、SQLite、原生 HTML 与 JavaScript。你可以选择其他适合本地原型的技术，但必须在系统设计中说明选择依据、适用条件和复杂度取舍。

以下内容不属于本次范围：

- 真实学校认证或其他真实身份认证；
- 支付、通知、候补、取消报名和公网部署；
- 分布式扩容或多机一致性保证；
- 收集本届资料未要求的信息。是否采集某项信息必须依据本届资料和字段说明，不能照搬往届表单。

固定虚构身份不等于真实认证。成果可以验证给定身份下的报名规则，但不能宣称能够阻止用户伪造多个身份。

## 三、必须提交的材料

所有成果放入当前用户与当前作业对应的目录：

`work/<学生UUID>/<作业UUID>/`

### 1. 可运行成果

包括页面、服务端、数据存储、测试所需文件及实际运行说明。项目可以由 AI 生成，但你必须能够解释关键规则的实际执行路径。

### 2. 需求依据

提交 `需求依据表.md`，至少覆盖：

- 如何识别同一学生；
- 哪些信息用于展示、保存或明确不采集；
- 名额、报名确认与剩余名额以什么为依据；
- 往届资料中哪些做法适用、哪些不适用。

每项至少写明：问题或规则、原始资料、版本与章节、短引文或准确摘要、适用性判断、自己的选择、设计影响、准备采用的验证方法。

技术检索结论可另建 `技术检索笔记.md`，作为需求依据的附录。技术结论应核查所选工具的官方文档，写明 URL、章节、访问日期和适用条件，不能只引用教程摘要或 AI 回答。

### 3. 系统设计

提交 `系统设计.md`，至少包括：

- 范围和不包含的功能；
- 关键规则及其需求依据编号；
- 一次报名从页面到接口、服务端判断、数据存储和响应的路径；
- 页面、接口、数据存储和验证各自负责什么、不负责什么；
- 接口输入、成功响应、重复报名、名额已满、无效输入和技术故障的分类；
- 稳定身份与展示信息的职责；
- 数据约束、容量检查与写入之间的关系；
- 失败、重试和中断时数据与响应应处于什么状态；
- 设计与实际实现之间的差异。

设计不要求使用特定框架或图形格式，但另一名开发者应能据此理解系统边界，不必猜测关键规则由哪里执行。

### 4. 验证报告

提交 `验证报告.md` 和可定位的原始结果。每项验证至少记录：

- 初始数据状态；
- 使用的测试身份或数据生成方式；
- 请求或操作；
- 预期结果；
- 实际 HTTP 响应；
- 最终持久化数据；
- 实际执行命令与原始结果位置；
- 结论与适用范围。

至少验证以下场景：

1. 首次正常报名；
2. 不同学生使用相同展示姓名；
3. 同一学生修改展示信息后再次报名；
4. 身份缺失、空值、空白或类型错误；
5. 同一学生并发提交 20 次；
6. 已有 99 人时，20 名新学生并发请求；
7. 已有 100 人时直接请求接口；
8. 停止并重新启动服务后读取记录。

测试全部通过可以得满分，不需要刻意制造失败。若出现真实失败，保留原结果，说明违反的规则、原因、修正和相同条件下的复测结果。不得删除、改写或虚构失败。

仅检查按钮、调用模拟函数、查看测试脚本是否存在，或引用 AI 的“全部通过”结论，都不能替代真实接口请求和数据核对。

### 5. 学习总结

提交 `学习总结.md`，说明：

1. 检索后改变了哪一个决定，依据是什么；
2. 自己提出或确认了哪些系统设计，为什么；
3. AI 完成了什么，自己核查了什么；
4. 说明你怎样核查 AI 的关键结论；发现问题就写出来，没有发现也说明核查方式与证据；
5. 当前结论成立在哪些条件下，仍未覆盖什么；
6. 如果增加取消报名并释放名额，首先需要重新检查什么。

不需要提交模型内部推理过程。需要说明的是你作出的判断、采用或拒绝 AI 建议的理由，以及实际核验结果。

### 6. README

提交 `README.md`，列出：

- 项目结构与范围；
- 运行时、依赖和版本；
- 可执行的安装、启动、停止命令；
- 访问地址、端口和数据库路径；
- 测试数据的位置与隔离方式；
- 主要成果、验证报告和原始结果的索引；
- 已知限制。

## 四、关键问题

完成后，你应能用自己的话回答：

1. 为什么某份资料适用于本届活动，另一份只能作为历史参考？
2. “同一学生只能报名一次”中的“同一学生”依据什么确定？
3. 页面校验、服务端判断和数据约束分别保障什么？
4. 两个请求争抢最后一个名额时，系统靠什么保持人数不超限？
5. 成功、重复、已满和技术故障在响应与数据上如何区分？
6. 哪些测试证明规则成立，哪些条件仍未被证明？
7. 你的方案在需求变化时需要先修改哪里？

教师可能根据提交材料和已确认分享的学习记录进行追问。回答应指向具体来源、实现位置或原始验证结果。

## 五、AI 使用规则

- 可以使用 AI 解释概念、检索资料、比较方案、生成代码、编写和执行测试。
- 必须回到原始业务资料和官方技术文档核对关键结论。
- 不得把 AI 生成的引用、日期、官方承诺或测试结果当作已核实事实。
- 不需要为了证明能力而手写代码，也不需要统计提示词数量或对话轮数。
- 可以向 AI 询问反例和替代解释，但最终选择和结论由你确认。
- 不得在成果中放入访问令牌、密钥、真实个人信息或其他敏感数据。

## 六、提交与分享

按应用中的提交流程确认分享本次成果。不要自行执行 Git 提交或推送，也不要调用系统凭据管理器。

提交时由应用使用当前连接的 GitHub 身份处理成果。提交只分享当次冻结的副本；提交后继续修改的文件，只有再次明确提交才会分享。

提交前请自行检查：

- 所有必需文件均位于当前作业成果目录；
- 使用虚构数据和独立测试数据库；
- 没有密钥、令牌或真实个人信息；
- README 中的命令可以执行；
- 验证报告能够定位到原始结果；
- 需求、设计与验证结论相互一致；
- 所有“待核实”内容都明确保留，没有改写成已确认事实。

## 七、评价

总分 100 分，四项各 25 分：

- 成果质量；
- 信息检索与判断；
- 系统设计；
- 质疑与验证。

具体细项和“待核实”规则见 `materials/评价标准.md`。评价不以代码由谁编写、提示词数量、对话长度或工具调用次数为依据。

若成果、原始结果或学习记录暂时无法读取，或某项判断需要你解释但尚未追问，相关细项会标为“待核实”。待核实项完成核实前，不计算总分。
