## 6. 证明边界

这里的“证明”只指：在当前实现、当前虚构数据和本机单进程环境中，有可复现的真实 HTTP 请求与 SQLite 记录支持。它不是对所有运行条件、所有并发调度或真实学校系统的形式化证明。

### 6.1 这些测试实际证明了什么

1. **输入边界在当前实现中生效**：空字符串、纯空白、首尾空格、制表符和换行被拒绝，返回 400 `invalid_student_id`，数据库没有新增记录，名额不变；内部空白没有被额外限制。测试覆盖了列出的样例，数据库 CHECK 也直接拒绝了这些样例及 NULL。
2. **身份和姓名按两条独立规则处理**：两个不同 `student_id` 可以使用同名并分别成功；同一 `student_id` 改名再次报名返回 409 `already_registered`，记录数仍为 1，原姓名和 `created_at` 未变。数据库的唯一键落在 `student_id`，不是姓名。
3. **在测试到的并发调度下，容量没有被突破**：已有 99 人时，20 个新学生同时请求，5 轮分别只产生 1 个 201 和 19 个 409 `full`，每轮最终正好 100 条，只存在一个本轮赢家。已有同一学生 20 次并发时，最终也只有 1 条记录。这支持“查重、查名额、写入在同一事务边界内”的实现判断，但不等于证明了所有可能的交错调度。
4. **忙碌路径有实际结果**：持有写锁时，接口经过 3 次尝试返回 503 `busy`，且没有留下记录；释放锁后可以成功报名。它证明的是这条锁定路径的响应和回滚结果，不是所有数据库故障都能被同样处理。
5. **结束进程并重启后数据仍在**：停止服务进程、使用同一个 SQLite 文件重新启动后，查询仍返回 `registered=true`、原姓名和原记录数。这证明持久化不依赖进程内缓存；不等同于崩溃恢复测试。
6. **数据库约束不是只写在文档里**：直接检查数据库，报名表只有 `student_id`、`name`、`created_at` 三列；NULL、空串、纯空白、首尾空白和重复 `student_id` 都被 SQLite 约束拒绝。它证明的是当前 schema 和当前 SQLite 版本的约束行为。
7. **页面能被真实服务提供并渲染**：HTML、CSS、JavaScript 由实际服务返回，Chrome 无头加载返回 200 并生成截图；页面中存在表单、查询控件、成功条件、重复/满额/超时分支和服务端名额展示代码。
8. **测试本身可以复现**：指定场景脚本为每个场景选择空闲端口、通过 `REGISTRATION_DB` 使用独立临时数据库，报名走真实 HTTP，最终直接查询 SQLite；结果写入 `verification/required-scenarios-results.json`，没有使用 mock、TestClient 或预置响应。

### 6.2 这些测试没有证明什么

1. **没有证明真实身份认证或防伪能力**。`student_id` 被当作测试平台提供的外部稳定标识；系统无法判断一个人是否伪造多个 `student_id`，也没有接入真实学校账户。
2. **没有证明完整浏览器交互流程**。浏览器检查只加载和渲染页面，没有自动填写表单、点击提交、等待响应并检查页面状态。页面里的 201、409、400、503 和超时分支是脚本条件检查，不等于这些分支已在真实浏览器中逐条触发。
3. **没有端到端证明“提交成功但响应丢失”**。V9 没有通过可控代理、断网或丢弃响应来注入；目前只分别验证了提交事务、只读查询和页面超时提示的存在。
4. **没有证明进程崩溃、断电或磁盘故障下的恢复**。S5 是在请求完成、数据库连接已释放后停止进程，再用同一数据库重启；不是事务中途强行终止进程，也不是灾难恢复演练。
5. **没有证明多进程、多机或分布式一致性**。并发验证在单机、单 SQLite 文件、单服务进程内完成；没有覆盖多个服务实例、网络文件系统、复制或分布式锁。
6. **没有证明生产负载能力**。5 轮 99+20 是容量规则验证，不是压力测试；没有测量大量用户、长时间运行、慢查询、磁盘满或其他资源耗尽时的表现。
7. **没有穷举所有 Unicode 空白和所有异常输入**。服务端规则按 Python `str.strip()` 的空白码点实现，测试覆盖了空格、制表、换行、全角空格等样例，但没有逐个验证全部 Unicode 码点，也没有穷举任意 JSON 结构。
8. **没有证明旧数据库迁移安全**。测试使用新 schema 和新数据库；如果已有旧表结构或历史记录，`CREATE TABLE IF NOT EXISTS` 本身不会完成迁移。
9. **没有证明取消报名、候补、名额释放、通知、支付或公网部署**。这些功能不在当前交付范围，相关并发和恢复规则也没有被测试。
10. **没有证明跨浏览器兼容性或公平性**。只在本机 Chrome 155、Windows 11 上加载过页面；并发赢家由调度和 SQLite 写入顺序决定，没有承诺公平排队或固定延迟。

### 6.3 要把这些边界变成可证明的结论，需要什么

- 用 Playwright、Selenium 等真实浏览器自动化，填写并提交表单，分别触发成功、重复、满额、输入错误、超时和查询刷新。
- 用可控代理或故障注入丢弃响应，验证“数据库已提交但客户端未确认”时的页面与只读查询行为。
- 在事务中途强制终止进程，验证 SQLite 恢复后的记录数和数据完整性。
- 启动多个服务进程或使用多机测试，明确 SQLite 文件访问方式，验证是否仍满足容量和唯一性规则。
- 进行有明确指标的压力/浸泡测试，记录吞吐、延迟、错误率和资源使用，而不是把 100 条业务名额当成压测结论。
- 对 Python `str.strip()` 的完整码点集合做逐项或属性测试，并补充异常 JSON、超大请求和边界长度测试。
- 接入真实身份系统后重新验证身份唯一性；若要部署到公网，还要评估认证、限流、CSRF、日志和隐私保护。

## 8. 结论成立的条件

本轮结论成立于：使用 2026 年本届通知和字段说明；`student_id` 是平台提供的非空稳定字符串；姓名只作展示；名额固定为 100；写入只经过当前服务进程和同一个 SQLite 数据库；首尾空白按 Python `str.strip()` 判断；忙碌事务总共尝试 3 次（含首次），每次重试前等待 50 毫秒。

超出这些条件时，应先重新核对需求和并发模型，不能直接沿用本报告的通过结论。
