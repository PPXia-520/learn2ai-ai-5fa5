## 一、UNIQUE 约束遇到 NULL

### 官方来源

- 链接：[SQLite CREATE TABLE, 3.6. UNIQUE constraints](https://www.sqlite.org/lang_createtable.html#unique_constraints)
- 页面标注更新时间：2025-04-30 20:02:34Z
- 访问日期：2026-10-21

原文：“For the purposes of UNIQUE constraints, NULL values are considered distinct from all other values, including other NULLs.”

### 文档明确保证

1. 对 UNIQUE 约束来说，NULL 与其他所有值都不同，包括与其他 NULL 也不同。因此，一个只声明 `UNIQUE` 的列可以容纳多个 NULL 值，这些 NULL 不互相冲突。
2. UNIQUE 和 NOT NULL 是两件不同的事。文档的 [NOT NULL constraints](https://www.sqlite.org/lang_createtable.html#not_null_constraints) 小节说明，NOT NULL 约束要求该列不能含 NULL；插入或更新为 NULL 会产生约束违反。
3. 文档没有把 UNIQUE 定义为“非空”或“非空白”校验。空字符串不是 NULL；空字符串、纯空白字符串和不同空白组合属于不同的值，UNIQUE 只比较值是否相同，不负责业务上的空白判定。

### 文档不保证或不能直接推出的内容

- 仅靠 `student_id` 上的 UNIQUE，不能推出“数据库会拒绝缺失或空白的 `student_id`”。没有 NOT NULL 等约束时，多个 NULL 可以同时存在。
- 文档没有规定本项目应使用 NOT NULL、CHECK、应用层校验，还是几者组合来拒绝空值和纯空白。这个选择尚未确认。
- UNIQUE 不能替代“每名学生只能有一条报名”的完整业务规则；它只提供值冲突检查，重复处理、响应分类和名额规则仍需应用逻辑。

### 对本项目要求的含义（只说明约束，不确认设计）

本届资料要求缺失或空白的学生标识不能产生有效报名。若数据库只写 `student_id TEXT UNIQUE`，该约束本身不会拒绝多个 NULL；如何补充空值和空白校验仍是一个需要明确决定的设计问题。对空字符串和纯空白的处理也不能仅从 UNIQUE 的 NULL 语义推出。

## 二、检查名额与写入报名怎样进入同一事务边界

### 文档明确保证

1. **原子提交**：文档写明，“Atomic commit means that either all database changes within a single transaction occur or none of them occur.” 同一事务内的数据库改动要么全部发生，要么全部不发生；事务中断时也保持原子提交的外观。这是把查询名额和插入报名放进同一事务后，能够避免只留下半条记录的依据。
2. **事务边界**：文档说明，数据库读写都在事务中发生；显式事务由 `BEGIN` 开始，并持续到 `COMMIT` 或 `ROLLBACK`。因此，检查名额和写入报名若放在同一个 `BEGIN` 与 `COMMIT` 之间，且中间没有提前提交，就属于同一事务。
3. **隔离与单一写者**：隔离文档写明，SQLite 的事务是 SERIALIZABLE；它通过串行化写入实现，同一时刻只有一个写事务。未提交的改动对其他连接不可见。因此，成功取得写事务后，其他写者不能同时提交并改变名额状态。
4. **DEFERRED 的实际行为**：默认是 DEFERRED。若 `BEGIN DEFERRED` 后第一条语句是 `SELECT`，会先启动读事务；后续写语句尝试升级为写事务，若其他连接已经在修改数据库，则升级可能失败并返回 `SQLITE_BUSY`。读事务期间，其他连接的新提交不会被这个连接看到，它继续看到事务开始时的历史快照。
5. **IMMEDIATE 的实际行为**：`BEGIN IMMEDIATE` 会让连接立即开始一个写事务，而不是等到第一条写语句。文档同时明确，如果另一个连接已有活动写事务，`BEGIN IMMEDIATE` 可能失败并返回 `SQLITE_BUSY`。
6. **提交也可能失败**：显式 `COMMIT` 在有未完成写操作时可能返回 `SQLITE_BUSY`；文档说明此时事务仍然活动，可以稍后重试。提交失败不等于事务已自动变成成功。
7. **busy timeout**：C 接口文档说明，busy timeout 会在表被锁时让 busy handler 睡眠指定时间；累计到指定毫秒后返回 0，使调用返回 `SQLITE_BUSY`。PRAGMA 文档提供同一设置的 SQL 入口，并说明每个连接只能有一个 busy handler。

### 文档没有保证的内容

- 文档没有提供一个名为“检查名额并写入”的单一 SQL 原语。事务负责把多条语句作为整体提交或回滚；`COUNT`、名额判断和 `INSERT` 仍需由应用写在同一个事务中。
- 文档没有保证 `BEGIN IMMEDIATE` 一定成功。它可能在开始时返回 `SQLITE_BUSY`；busy timeout 只是等待一段时间，超时后仍然返回忙碌。
- 文档没有保证应用会自动重试事务、自动重新读取名额或自动选择正确的提交时机。重试策略和失败响应仍需设计。
- 文档没有保证 DEFERRED 事务先读后写时能获得最新名额；读事务看到的是快照，后续升级写事务可能失败。因此“先 COUNT 再 INSERT”若不在正确的写事务边界内，不能仅凭 SQLite 的事务机制推出容量规则成立。
- 文档没有替本项目决定是否使用 IMMEDIATE、是否设置 NOT NULL、是否加 CHECK、busy timeout 取值、重试次数、HTTP 状态码或重复报名的响应格式。

### 文档层面的操作边界（不是已确认设计）

从上述文档可以描述的机制是：把“查询有效报名数、判断是否已满、插入报名”放在同一个显式事务中，并在这些语句之间不执行 `COMMIT` 或 `ROLLBACK`；事务成功提交时，全部改动原子生效，失败回滚时不会留下半条记录。若希望从事务一开始就取得写事务资格，文档描述的入口是 `BEGIN IMMEDIATE`；若使用默认的 `BEGIN DEFERRED` 且先执行查询，文档明确说明后续写操作可能需要升级，并可能得到 `SQLITE_BUSY`。

以上只是文档机制的组合说明，不表示本项目已经选定 `BEGIN IMMEDIATE`、DEFERRED、busy timeout 数值或重试策略。需要在系统设计中另行确认并验证。
