## 1. 范围与不包含的功能

本原型包含一个可操作的报名页面、接收报名请求的服务端接口、SQLite 持久化存储，以及针对真实接口和数据库状态运行的验证设计。使用课程提供的虚构学生样本，不接入真实学校账户系统。

不包含：真实学校登录或其他真实身份认证、支付、消息通知、候补、取消报名、公网部署、分布式多机一致性。课程原型不能阻止用户伪造多个 `student_id`，只能验证给定虚构身份下的规则。

## 3. 数据模型与约束

本原型的报名记录只包含实现本届规则所需的信息：

| 字段 | 约束与含义 | 负责层 |
| --- | --- | --- |
| `student_id` | 原始字符串必须非空；按 Python `str.strip()` 判断，首尾不得有空白；直接拒绝，不做 `strip` 或身份改写；内部空白不额外限制；NOT NULL；UNIQUE；CHECK 作为数据库兜底 | 接口校验为主，数据库约束兜底 |
| `name` | 非空字符串，纯空白不视为有效；仅作展示；不唯一；首次有效报名时保存；同一 `student_id` 再次报名不覆盖 | 接口校验和写入，数据库 NOT NULL 兜底，页面展示 |
| `created_at` | 首次成功写入的服务端时间，用于核对记录；不影响身份和名额 | 数据保存层 |

不建立手机号、身份证号或住址字段，也不把它们用于身份或查重。

### 3.1 身份字段的约束一致性

接口校验的是请求中的原始字符串，不允许先去掉首尾空白再保存。`student_id` 为空字符串、纯空白或首尾带空白时，请求在进入事务前被拒绝。首尾空白按 Python `str.strip()` 的字符集判断；内部空白不额外限制，因为字段说明没有要求。

数据库的 NOT NULL 和 CHECK 是兜底，不应被当成接口校验的替代品。SQLite 的 UNIQUE 对 NULL 有特殊语义：NULL 彼此不冲突，因此仅靠 UNIQUE 不能拒绝空值，必须同时有 NOT NULL。CHECK 必须覆盖与 Python `str.strip()` 相同的首尾空白字符集，不能接口拒绝制表符、换行或 Unicode 空白而数据库只检查普通空格。数据库无法单独表达“表中最多 100 行”的业务容量规则。

### 3.2 姓名与重复报名

第一次成功报名时保存提交的姓名。后续同一 `student_id` 的请求即使带了不同姓名，也不新增记录、不更新姓名，响应展示第一次保存的姓名。姓名不建立唯一约束，同名不同 `student_id` 可以分别报名。

| 编号 | 规则 | 主责层 | 配合层 | 执行点 | 失败结果 |
| --- | --- | --- | --- | --- | --- |
| K1 | `student_id` 必须是非空字符串；首尾有空白直接拒绝，不 `trim`、不改写 | 报名接口 | 页面做提示；数据库 NOT NULL 和 CHECK 兜底空值与空白，UNIQUE 防止重复；测试绕过页面验证 | 接口在开始事务前检查原始值；数据库在写入时复核 | 输入错误；不建记录、不占名额、不进入事务 |
| K2 | 同一 `student_id` 只能有一条报名记录 | 报名接口的查重逻辑和数据库 UNIQUE 共同保证 | 页面只展示服务端结果；测试检查记录数 | 事务内先按 `student_id` 查重；数据库唯一约束防止并发写入重复 | 重复报名；不新增、不覆盖姓名，返回“已报名” |
| K3 | 查重、查名额和写入必须在一个 `BEGIN IMMEDIATE` 事务中完成；遇忙碌整个事务重来，总尝试最多 3 次（含首次） | 报名接口/服务层 | 数据库提供事务、单写者和原子提交；测试验证忙碌和回滚 | 每次尝试从 `BEGIN IMMEDIATE` 开始；所有判断和插入在同一事务；每次忙碌重试前等待 50 毫秒；提交成功后才返回成功 | 3 次尝试仍忙碌则技术故障；事务回滚，不留下半条记录 |
| K4 | 先查重，再查名额；已报名学生在满额时也返回“已报名” | 报名接口/服务层 | 数据库唯一约束支持查重；页面按结果展示 | 同一事务内先查是否存在该 `student_id`，存在则直接走重复分支，不再判断名额 | 返回 `already_registered`，不因满额改报 `full` |
| K5 | 剩余名额只使用服务端返回的数；请求超时提示“结果未确认，请刷新查询” | 报名接口计算并返回；页面只展示 | 数据库提供持久化记录；只读查询接口用于刷新；测试模拟响应丢失 | 服务端从持久化记录计算剩余名额；页面不本地减一；超时后不推断成功或失败，调用只读查询 | 超时为“未确认”状态，不是成功也不是名额已满 |
| K6 | 姓名作为展示信息保存；同一 `student_id` 再次报名不覆盖原姓名 | 报名接口和服务层 | 数据库 NOT NULL；页面展示服务端保存的姓名 | 新记录写入时保存姓名；重复分支不执行姓名更新 | 重复请求保留原姓名，返回原记录信息 |

## 5. 一次报名的完整路径

1. 页面提交 `student_id` 和姓名。页面可以先做提示，但最终判断不依赖页面。
2. 报名接口读取原始请求，校验 `student_id` 和姓名。`student_id` 不是字符串、为空、纯空白、首尾有空白，或姓名不合法时，直接返回输入错误；此时不开启事务、不写记录、不占名额。
3. 报名接口进入事务尝试。总尝试次数最多 3 次，包含首次；每次忙碌后等待 50 毫秒，再从新的 `BEGIN IMMEDIATE` 开始完整重试。
4. 在事务内先按 `student_id` 查重。若已存在，读取当前服务端剩余名额，结束事务，返回 `already_registered`。此分支不检查是否满额，也不修改姓名。
5. 若不存在，统计当前有效报名数。若已达到 100，结束事务，返回 `full`，不写入。
6. 若未满，写入一条新记录，姓名取本次请求的值。写入后提交事务。
7. 提交成功后才生成成功结果和剩余名额。提交返回忙碌或失败时，不得返回成功；应按第 7 节处理。
8. 页面只对明确的 `registered` 结果显示成功；其他结果按第 7 节分类展示。剩余名额直接使用响应中的服务端数字。

### 5.1 事务与重试边界

每次尝试的顺序是：开始 `BEGIN IMMEDIATE`，查重，查名额，写入，提交。这些步骤属于同一个事务；中途不能提交，也不能把上一次尝试的查重或名额结果带到下一次。所有报名写入路径都必须遵守这条边界；测试预置数据应在独立准备阶段完成，不能混入并发报名场景。

遇到 `SQLITE_BUSY` 时，无论发生在开始事务、查询、写入还是提交阶段，都结束当前事务，等待 50 毫秒后从第一步重新尝试。总尝试次数达到 3 次（含首次）仍忙碌，返回技术故障；不能返回“名额已满”或“已报名”。非忙碌的数据库错误走技术故障路径，不进行业务性重试。

## 6. 接口契约

### 6.1 报名接口

请求为 `POST /api/registrations`，提交以下字符串字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `student_id` | 是 | 非空字符串；首尾无空白；保留原值，不 `trim` |
| `name` | 是 | 非空字符串；仅用于展示；不要求唯一 |

响应同时包含 HTTP 状态和明确的 `result`。页面不能只看状态码，也不能把任意 2xx 当成报名成功。

| 场景 | HTTP | `result` | 数据变化 | `remaining` | 页面含义 |
| --- | --- | --- | --- | --- | --- |
| 新报名成功 | 201 | `registered` | 新增 1 条，保存本次姓名 | 服务端当前剩余名额 | 显示“报名成功” |
| 同一学生已报名 | 409 | `already_registered` | 不新增、不更新姓名，即使已满也走此分支 | 服务端当前剩余名额 | 显示“已报名”，显示原保存姓名 |
| 新学生遇到满额 | 409 | `full` | 不新增 | 服务端当前剩余名额，通常为 0 | 显示“名额已满” |
| 身份或姓名无效 | 400 | `invalid_student_id` 或 `invalid_name` | 不新增、不占名额 | 可省略；页面显示输入错误 | 显示具体输入问题 |
| 3 次尝试仍忙碌 | 503 | `busy` | 回滚，不留下本次记录 | 可省略；刷新查询以服务端为准 | 显示技术忙碌，不显示成功或已满 |
| 其他存储故障 | 500 | `storage_error` | 回滚；若无法确认则走未确认查询 | 不提供或由查询接口提供 | 显示技术故障 |

### 6.2 刷新查询接口

为了让超时后的“请刷新查询”可执行，接口层提供一个只读查询入口：`GET /api/registrations/{student_id}`。

查询结果至少包含：该 `student_id` 是否已报名、报名时保存的姓名（若存在）、服务端当前剩余名额。查询只读，不新增记录、不占名额、不更新姓名。页面超时后调用该入口，不自动重复提交；查询发现已报名时展示已报名，查询发现未报名时由用户决定是否再次提交。

## 7. 失败、回滚与未知状态

| 情况 | 持久化状态 | 服务端处理 | 页面处理 |
| --- | --- | --- | --- |
| 输入无效 | 无记录 | 400；未进入事务 | 显示输入错误；不显示成功 |
| 事务开始或语句执行遇忙碌 | 当前事务回滚 | 每次从新事务重试，总尝试最多 3 次 | 等待结果；3 次尝试失败显示技术忙碌 |
| 提交遇忙碌 | 当前事务未提交；结束事务后重试 | 不回成功；从新事务重试 | 不显示成功 |
| 进程在事务中途中断 | SQLite 原子回滚，无半条记录 | 进程恢复后重新查询 | 刷新查询确认 |
| 提交成功但响应丢失 | 记录已提交 | 客户端无法确认服务端结果 | 显示“结果未确认，请刷新查询”；不自动重复提交 |
| 重复请求 | 原记录保留 | 返回 `already_registered` | 显示已报名和原姓名 |
| 唯一约束冲突 | 不新增第二条 | 回滚后重新查询；若已有记录则返回已报名，否则技术故障 | 按服务端结果展示 |

## 8. 验证设计

验证必须通过真实 HTTP 请求并核对数据库最终状态，不能只检查按钮、页面文字或 mock 返回。每个场景记录初始数据、请求、响应、最终记录数和剩余名额。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| V1 | `student_id` 缺失、null、数字、空字符串、纯空白、首尾空格、首尾制表或换行 | 全部拒绝；无记录；名额不变 |
| V2 | 两个不同 `student_id` 使用同名 | 两条记录都成功；姓名不唯一 |
| V3 | 同一 `student_id` 首次报名后改名再次报名 | 记录数仍为 1；原姓名不变；返回已报名 |
| V4 | 已满 100 人时同一已报名学生再次请求 | 返回 `already_registered`，不是 `full`；记录数和姓名不变 |
| V5 | 已有 99 人时 20 名新学生并发请求 | 只新增 1 条，总数不超过 100 |
| V6 | 同一学生并发提交 20 次 | 最终只有 1 条记录，其他请求返回已报名或正确业务结果 |
| V7 | 已有 100 人时新学生直接请求接口 | 返回 `full`，不新增 |
| V8 | 制造数据库写锁，使事务连续 3 次尝试均忙碌 | 最终返回 `busy`；无部分记录；释放锁后可重新成功报名 |
| V9 | 提交成功但客户端丢失响应 | 数据库已有记录；页面显示未确认；只读查询显示已报名，不新增第二条 |
| V10 | 停止并重启服务后查询 | 已确认记录、姓名和人数保持 |
| V11 | 直接读取数据库，检查字段和约束 | 没有手机号、身份证号或住址字段；NULL、空串、纯空白和首尾空白无法绕过约束 |
| V12 | 页面面对 201、409、400、503 和超时 | 只在 `registered` 时显示成功；其余显示对应结果；超时显示“结果未确认，请刷新查询” |

## 9. 实现说明与差异

以下内容对应实际实现，验证报告可以引用本次结果：

1. “最多 3 次”按总尝试次数实现，包含首次；每次失败后等待 50 毫秒。SQLite 连接还设置了 50 毫秒 busy timeout，因此每次尝试可能先在锁上等待，再计入一次尝试。实测锁定期间 3 次尝试约 0.464 秒返回 503，且无记录。
2. 首尾空白按 Python `str.strip()` 判断。数据库 CHECK 使用同一组 Python 空白码点生成，覆盖空格、制表符、换行、回车和 Unicode 空白；接口和数据库都已拒绝首尾空白。页面即时提示也使用同一组码点，不再依赖 JavaScript `trim()` 的字符集。
3. `student_id` 内部空白不额外限制；接口和数据库都允许 `S 2026` 这类包含内部空白的字符串，并保留原始值。
4. 忙碌重试前等待 50 毫秒；总尝试次数为 3 次。没有把忙碌映射成 `full` 或 `already_registered`。
5. HTTP 状态码和响应字段按第 6 节实现：201 `registered`、409 `already_registered`、409 `full`、400 `invalid_*`、503 `busy`、500 `storage_error`。
6. 查询接口已实现为 `GET /api/registrations/{student_id}`，返回是否报名、首次保存的姓名和服务端剩余名额。
7. 剩余名额由服务端在事务内根据持久化记录计算并返回，页面不本地减一；成功响应只使用服务端结果。
8. 页面使用 8 秒客户端超时；超时或网络结果不明时显示“结果未确认，请刷新查询”，不自动重复提交，查询按钮调用只读接口。
9. 页面验证由真实 HTTP 资源与脚本分支检查组成；另用本机 Chrome 无头加载首页，确认 HTML、CSS、JavaScript 能由真实服务提供并在浏览器中渲染，截图见 `verification/page-8000.png`。本轮没有进行浏览器自动点击或表单提交测试；浏览器渲染成功不等于点击流程已被自动验证。
